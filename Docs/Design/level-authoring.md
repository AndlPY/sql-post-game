# Рівні, когорти та завдання

Точка входу: `src/levels.ts`. Єдиний склад, тип Parcel і список полів: [src/data/parcels.ts](../../src/data/parcels.ts). Замовлення рівня 1 — content.ts; demo/SQL-вступ — tutorial-content.ts. Рівень 2 — levels.ts. Стан перевірок — `implementation-status.md` (локально), чинні рішення — [backlog](mvp-backlog.md).

## Спільна механіка

- Рівень визначає тему, назву, синтаксис, demo, tutorial та orders. Власного каталогу більше немає: DB і видача використовують одну parcels.
- Зараз у складі 36 рядків: об’єднані 28 старих і 8 додаткових посилок повторних одержувачів. Номери старих посилок збережено; колір 2121 змінено з purple на pink, щоб фіолетова коробка рівня 1 залишалася однозначною.
- Worker створює спільний seed один раз, не замінює таблицю між рівнями. Після recovery створює той самий склад. Видані посилки поки залишаються в таблиці — зміна цього правила відкладена в Q11.
- Клієнт 0 — окремий від 13, без винагороди/спроб/зірок. Основні: 4 easy × 10, 4 medium × 20, 4 review × 10; bonus × 30 останній. Максимум 190 монет.
- Shuffle easy/medium, по 2 випадкові review у кожній половині; стабільний parcelId не залежить від позиції.
- Дозволений SELECT з одним правильним id приймається незалежно від оператора/вибору інших колонок. SELECT * дозволено. `solution` — приклад видачі, `search` рівня 2 — авторський приклад пошуку; ці поля не є перевіркою SQL гравця.
- Кілька результатів у preview допустимі: зіставити всі відомі ознаки, прочитати id і уточнити запит перед Run. AND/OR до рівня 3 не потрібні.
- Прогрес і зірки окремі для рівнів; рівень 2 відкривається за 3★ першого. Старі збереження належать рівню 1.

## Єдиний порядок авторства реплік

1. Визначити тему, когорту й уже вивчені засоби. Easy — пряма ознака; medium — перетворення одиниць, виправлення помилкового спогаду чи додатковий крок; review — попередній матеріал; bonus — кілька міркувань без ненавченого синтаксису.
2. Спочатку написати пошуковий SQL для потрібної навички. Вибрати цільову посилку з єдиного складу, визначити завершальний запит видачі. Якщо пошук повертає кілька рядків, явно встановити, які відомі клієнту ознаки відрізняють ціль.
3. Звірити ці ознаки з усім складом. Їх сукупність має визначати рівно один id. Прізвища, імена й навіть повні одержувачі можуть повторюватися. Самотня умова «не коричнева» без іншої достатньої ознаки непридатна, якщо їй відповідає багато посилок.
4. Перевірити очевидні обходи: для нової теми не повідомляти точний id чи унікальне ім’я, що одразу дають відповідь через =. У рівні 2 одержувачі easy/medium мають по дві посилки; порівняння відрізняє одну. Альтернативні правильні SQL дозволені: примусового контролю оператора немає.
5. Перетворити факти на природну репліку від першої особи. Клієнт знає власне ім’я, номер із повідомлення, вагу/колір зі слів відправника чи квитанції. Він не знає назви колонок, внутрішню полицю чи вміст усього складу.
6. За бажанням додати коротку побутову деталь. Вона не повинна суперечити ознакам, приховувати потрібну інформацію або створювати нову умову пошуку. Виправлений спогад має мати чітку остаточну версію.
7. Окремо написати пояснення наставника: назви SQL-полів, одиниці, значення кольорів, приклад пошуку й видачі. Клієнт не каже «виведи id та shelf», «у базі це brown» або «використай WHERE».
8. Перевірити SQL на повному спільному наборі, однозначність ознак, граничні значення (> не включає рівність), tutorial і відповідність репліки даним. Агент зараз виконує лише статичний перегляд; tests/playtest запускає користувач.

Не писати від імені клієнта «це єдина така коробка на складі» або «в мене тут одна посилка» як заміну перевірці даних. Не додавати автоматично повне ім’я до кожної репліки. Не штрафувати за вибір зайвих колонок. Не заявляти, що довільні 1000 нових рядків гарантовано збережуть однозначність старих завдань.

Це правила авторства, а не процедурний генератор у runtime. Персонаж/портрет вибираються незалежно від SQL-завдання; репліки бажано формулювати без прив’язки до статі зображення.

## Розширення parcels після research

Нових колонок зараз не додано. Наступна зміна схеми має разом охопити тип/дані у data/parcels.ts, SQL schema/seed, schema UI, репліки, tutorial, приклади й перевірки. Стабільний id лишається ключем видачі. Джерело даних одне; заборонено вводити приховані каталоги чи фільтри для окремого рівня.

Після додавання рядків перевірити всі рівні, не лише новий: унікальна фіолетова коробка або вага можуть стати неоднозначними. Якщо бракує вже вивчених ознак, перепроєктувати завдання або дочекатися відповідної теми. Не обходити проблему прихованим видаленням рядків чи вимогою ненавченого AND.

Ліміт preview зараз 100 рядків. Перед збільшенням складу до сотень/тисяч потрібне окреме рішення щодо preview/pagination, продуктивності та стартового SELECT *; поточний код не оголошується готовим до 1000 рядків.

`defineLevel` перевіряє id, наявність цілей, когорти та безоплатність demo, але не розуміє природну мову. У tests/core.test.ts додано перевірку пошукових прикладів рівня 2 на спільному складі та неоднозначності самих прізвищ; це не заміна редакторському перегляду й playtest. Стан запусків і gameplay feedback — лише в `implementation-status.md` (локально).
